# Signup page and its endpoint

The website is static files on GitHub Pages. It can read things, which is how
the calendar works, but it cannot hold a service account key, so it cannot
write to the membership sheet. A small Google Apps Script bound to that sheet
does the writing.

This is not just plumbing. The script is where every rule that matters is
enforced, because a browser form can be edited by anyone who opens the
developer tools:

- **Only public ministries can be self-selected.** Nobody adds themselves to
  `youth-leaders` or `worship` no matter what their browser sends.
- **The allowed list comes from the site's own `events.json`**, which by
  construction lists only public ministries, so it cannot drift out of step
  with the job's config.
- **Tokens are generated by the script**, never accepted from the caller.
- **Signing up twice with the same email updates the existing row** instead of
  issuing a second calendar, which would leave an orphaned feed on somebody's
  phone that nobody can revoke because nobody knows it exists.
- **Private columns are never written**, even when updating an existing person.
  A leader's decision stays a leader's decision.

## Deploying it

Signed in as the church Google account.

1. Open the **Calendar Permissions** spreadsheet.
2. **Extensions** > **Apps Script**. A new tab opens with an empty `Code.gs`.
3. Delete whatever is in there and paste the whole contents of
   [`site/apps-script/Code.gs`](../site/apps-script/Code.gs).
4. Click the project name, top left, and rename it `GLBC Signup`.
5. Save, the disk icon or Ctrl+S.
6. **Deploy** > **New deployment**.
7. Click the gear next to "Select type" and choose **Web app**.
8. Fill in:
   - **Description**: `signup`
   - **Execute as**: **Me** (the church account). This is what lets it write
     to the sheet without anyone signing in.
   - **Who has access**: **Anyone**. This means anyone may call the endpoint,
     not that anyone can read the sheet. The script decides what it will do,
     and it refuses everything except adding a person to public calendars.
9. **Deploy**. Google asks you to authorise it the first time. It will warn
   that the app is not verified, which is expected for a script you just wrote
   yourself: choose **Advanced**, then **Go to GLBC Signup (unsafe)**, then
   **Allow**.
10. Copy the **Web app URL**. It looks like
    `https://script.google.com/macros/s/AKfy…/exec`.

Then send me that URL, or put it in yourself: it goes in
`job/config/ministries.json` as `site.signupEndpoint`. The job publishes it
into `events.json`, so the page needs no separate config file.

Until it is set, the signup page says signup is not switched on yet rather
than showing a form that cannot work.

## Checking it worked

Open the web app URL directly in a browser. A `GET` returns:

```json
{"ok":true,"service":"glbc-signup"}
```

That confirms the deployment is alive without writing anything.

Then use the real page at `/signup.html`, sign yourself up for one public
calendar, and check that a row appears on the People tab with a token in it.
The feed itself appears after the next hourly sync.

## When you change the script

Apps Script keeps serving the **deployed version**, not the saved one. After
editing, go to **Deploy** > **Manage deployments**, click the pencil, set
**Version** to **New version**, and Deploy. The URL stays the same. Forgetting
this step is the usual reason a change appears to have no effect.

## What it deliberately does not do

- It does not delete anybody. Removing a person is a leader editing the sheet.
- It does not touch private ministry columns, in either direction.
- It does not email anyone. There is no mail sending anywhere in this system.
- It does not read anything back out to the caller beyond that person's own
  token and feed URL.
